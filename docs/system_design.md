# แบบระบบ ERPLPH — ใช้งานพร้อมกัน 300–400 คน

ร่าง 11 กันยายน 2569 · ข้อที่มีเครื่องหมาย **[รอตัดสิน]** ยังต้องให้ผู้ใช้ยืนยัน

## 1. เปลี่ยนจากแดชบอร์ด เป็นระบบทำงาน

เดิมตั้งใจเป็นแดชบอร์ดให้ผู้บริหารดู ตอนนี้ขอบเขตคือ **ที่ทำงานของทุกฝ่ายที่เกี่ยวกับ
ของและเงิน** ผู้ใช้ 300–400 คนต่อวัน ช่วงสิ้นเดือนเข้าพร้อมกันมาก

| ผู้ใช้ | ใช้ทำอะไร |
|---|---|
| รองผู้อำนวยการฝ่ายบริหาร | ภาพรวม 8 ตัวเลข แนวโน้ม ส่งออกเข้าที่ประชุม |
| งานจัดซื้อ | รายการที่ต้องสั่ง · ใบ PO ค้าง/รอลงนาม/รอส่งบริษัท/เลยกำหนด · บันทึกการติดตาม · ซื้อซ้ำ · ผลงานบริษัท (ส่งตรงเวลาไหม) · เทียบแผนจัดซื้อ |
| งานรับของ | ของที่จะเข้าวันนี้/สัปดาห์นี้ · รับแล้วแต่เอกสารเบิกจ่ายยังไม่ครบ |
| คลังและห้องจ่าย | ใกล้หมดอายุ → โอนไปคลังที่ใช้ทัน · ค้างนิ่ง · คลังย่อยขาดแต่คลังหลักมี |
| การเงิน | เจ้าหนี้ค้างจ่ายตามอายุหนี้ · ค้นสถานะจ่ายเงินตามบริษัท/ใบแจ้งหนี้ |
| ช่าง | เครื่องช่วยหายใจ: อยู่ที่ไหน สถานะ คิวรอซ่อม อะไหล่มีในคลังไหม แผนบำรุงรักษา |
| ทุกคน | ค้นหาเดียวครอบคลุม (รายการ เลขใบ PO ใบรับ บริษัท เลขครุภัณฑ์) · หน้า "งานของฉัน" |

## 2. หลักการที่ไม่เปลี่ยน

1. **SSB เป็นระบบบันทึกหลัก ERPLPH ไม่เขียนลง SSB** การเขียนตรงลงฐานข้อมูลของ
   ระบบอื่นข้ามกติกา การอนุมัติ และประวัติของระบบนั้น ใบสั่งซื้อจริงยังออกใน SSB
   ERPLPH ช่วยตัดสินใจ ติดตาม และบันทึกงานที่ SSB ไม่มีที่เก็บ **[รอตัดสิน: ยืนยันว่า
   "สั่งซื้อ" หมายถึงแบบนี้ ถ้าต้องการออกใบในระบบนี้จริง ต้องมีช่องทางนำเข้าที่ผู้ผลิต
   SSB รองรับ]**
2. **ผู้ใช้ไม่ทำให้เซิร์ฟเวอร์โรงพยาบาลช้าลง** ทุกหน้าอ่านจากฐานข้อมูลของ ERPLPH
   เท่านั้น มีตัวดึงตัวเดียวที่อ่าน SSB ตามรอบและพักระหว่างคำสั่ง คนเข้า 400 คน
   หรือ 4,000 คน SSB ก็รับภาระเท่าเดิม (บทเรียนจาก Stock5: กระดิ่งแจ้งเตือนสั่ง sync
   ทุก 5 นาทีเมื่อมีคนเปิดหน้า)
3. **ไม่เดา** ตามกติกาใน README
4. **ไม่เก็บข้อมูลผู้ป่วย** ข้อมูลในระบบเป็นระดับรายการ คลัง และหน่วยงาน

## 3. โครงสร้าง

```
SSB (อ่านอย่างเดียว)
   │  ตัวดึงตามรอบ · พักระหว่างคำสั่ง · ตัวเดียวทั้งระบบ
   ▼
warehouse.db ── ข้อมูลที่ดึงมา (ดึงใหม่ได้เสมอ)
   │  คำนวณล่วงหน้าหลังดึงทุกรอบ
   ▼
ตารางสรุป ── ตัวชี้วัด รายการที่ต้องทำ ดัชนีค้นหา (หน้าเว็บอ่านตรงนี้ จึงเร็ว)
   │
   ▼
เว็บ API ◄──► work.db ── ข้อมูลที่ผู้ใช้สร้าง: การติดตาม มอบหมาย หมายเหตุ งานซ่อม
   │                     ประวัติการกระทำ (ข้อมูลเดียวที่หายแล้วดึงคืนไม่ได้ ต้องสำรอง)
   ▼
หน้าเว็บ (Angular เหมือน Stock5) · ใช้บนมือถือได้ · 172.16.13.102/ERPLPH
```

แยก warehouse.db กับ work.db เพราะตอนตัวดึงเขียนงวดใหญ่ ฐานข้อมูลถูกล็อกการเขียน
หลายวินาที ถ้าอยู่ไฟล์เดียวกัน ผู้ใช้ที่กดบันทึกช่วงนั้นจะค้าง

## 4. ความสดของข้อมูล

ทุกหน้าแสดง "ข้อมูล ณ เวลา" เสมอ

| ข้อมูล | รอบที่เสนอ | วิธี |
|---|---|---|
| ใบ PO และใบรับ | ทุก 15–30 นาที ในเวลาราชการ | ดึงเฉพาะที่เปลี่ยนตั้งแต่รอบก่อน |
| คงคลัง | ทุก 1 ชั่วโมง | ภาพคงคลัง (คำสั่งเบา) |
| ใบจ่าย / ยอดใช้ | ส่วนเพิ่มทุก 1 ชั่วโมง · ทั้งเดือนตอนกลางคืนเพื่อเก็บตก | สอบทานรายล็อตเหมือนเดิม |
| ย้อนหลังและเดือนที่ปิดแล้ว | เมื่อคำสั่งหรือกติกาหน่วยเปลี่ยนเท่านั้น | ตามลายนิ้วมือที่มีอยู่ |
| การเงิน ครุภัณฑ์ สัญญา | รอเอกสาร | — |

ต้องวัดภาระจริงบน SSB ก่อนตั้งรอบถี่ขนาดนี้

## 5. รองรับคนพร้อมกัน

ประมาณการ: 400 คนต่อวัน · สิ้นเดือนพร้อมกัน 100–150 คน · ราว 10–20 คำขอต่อวินาที

- หน้าเว็บอ่านตารางที่คำนวณไว้แล้ว ไม่คำนวณตอนเปิดหน้า เป้าหมายตอบภายใน 1 วินาที
  ที่ 95% ของคำขอ ในช่วงพีค
- ไฟล์หน้าเว็บตั้งชื่อตามเนื้อหาและแคชถาวร หน้าเปลือกไม่แคช (บทเรียนจาก Stock5)
- แบ่งหน้า ย่อข้อมูลก่อนส่ง ไม่ส่งตารางทั้งก้อน
- **ทดสอบโหลดจำลองช่วงสิ้นเดือนก่อนเปิดใช้จริง** ไม่เดาว่าเครื่องรับไหว
- **สเปกเครื่องเว็บ 172.16.13.102 — ได้แล้ว 16 ก.ย. 2569** (ภาพ msinfo32 จากผู้ใช้)

  | รายการ | ค่า |
  |---|---|
  | ชื่อเครื่อง | `LPH-SERVICE` (เครื่องเสมือนบน VMware รุ่น VMware7,1) |
  | ระบบปฏิบัติการ | Windows Server 2022 Datacenter · 10.0.20348 Build 20348 |
  | ซีพียู | Intel Xeon Gold 6248 @ 2.50GHz — 4 ซ็อกเก็ต × 2 คอร์ = **8 คอร์** |
  | หน่วยความจำ | **16 GB** (ตอนถ่ายใช้ไปราว 5.2 GB เหลือ 10.8 GB) · page file 2.38 GB |
  | อื่น ๆ | UEFI + Secure Boot เปิด · เขตเวลา SE Asia · Windows ยังไม่ได้ activate |

- **ฐานข้อมูล SSB อยู่คนละเครื่อง: `172.16.0.33:1433`** (จาก config ของ ERPLPH/Stock5) —
  กติกาข้อ 2 "ไม่ทำให้เซิร์ฟเวอร์โรงพยาบาลช้าลง" จึงหมายถึงเครื่อง **172.16.0.33** เป็นหลัก
  ไม่ใช่เครื่องเว็บที่ถ่ายมา ส่วน 16 GB ของ LPH-SERVICE เป็นภาระของ Stock5 + ERPLPH เอง
- **[รอตัดสิน]** สเปกเครื่องฐานข้อมูล 172.16.0.33 (CPU, RAM, ดิสก์) และใช้ร่วมกับระบบอื่น
  (เช่น HIS) หรือไม่ · มีโปรแกรมอื่นรันบน LPH-SERVICE ด้วยไหม · พื้นที่ดิสก์ว่างของทั้งสองเครื่อง

## 6. ล็อกอินและสิทธิ์

- ใช้บัญชีที่เจ้าหน้าที่มีอยู่แล้ว ไม่สร้างรหัสผ่านชุดใหม่ Stock5 ตรวจกับบัญชีห้องยา
  (SYSCONFIG รหัส 10000) ซึ่งช่างและผู้บริหารอาจไม่มี **[รอตัดสิน: ทุกฝ่ายมีบัญชี SSB
  ไหม ถ้าไม่มี โรงพยาบาลมีบัญชีกลางอื่นไหม เช่น HIS หรือ Active Directory]**
- session เก็บลงฐานข้อมูล ไม่เก็บในหน่วยความจำ รีสตาร์ตแล้วผู้ใช้ไม่หลุด
- บทบาท: ผู้บริหาร · จัดซื้อ · รับของ · คลัง (จำกัดตามคลัง) · การเงิน · ช่าง · ผู้ดูแลระบบ
  ผู้ดูแลระบบกำหนดบทบาทให้แต่ละคน
- บันทึกทุกการกระทำ: ใคร ทำอะไร เมื่อไร กับเอกสารไหน

## 7. งานของช่าง: เครื่องช่วยหายใจ

SSB มี "คลังศูนย์เครื่องช่วยหายใจ" (คลัง 9) แต่ยังไม่รู้ว่าเก็บตัวเครื่องรายเครื่อง
หรือเก็บแค่วัสดุสิ้นเปลือง และยังไม่รู้ว่างานซ่อมบันทึกที่ไหน **[รอตัดสิน: ตอนนี้แจ้งซ่อม
และติดตามงานซ่อมทำอย่างไร — กระดาษ Excel LINE หรือโปรแกรม]** ถ้ายังไม่มีระบบใดเก็บ
ERPLPH จะเป็นเจ้าของข้อมูลงานซ่อมเอง (อยู่ใน work.db) และเชื่อมกับคลังเพื่อบอกว่า
อะไหล่มีหรือไม่

## 8. ดูแลรักษา

- หน้าสุขภาพระบบ: รอบดึงล่าสุด งวดที่ล้ม ความสดของข้อมูลแต่ละชนิด
- แจ้งผู้ดูแลเมื่อดึงล้มหรือข้อมูลเก่าเกินกำหนด
- สำรอง work.db ทุกคืน และก่อนอัปเดตทุกครั้ง
- ถ้า SSB ล่ม ระบบยังเปิดได้ด้วยข้อมูลล่าสุด พร้อมแถบแจ้งเตือน
- อัปเดตผ่าน git แบบเดียวกับ Stock5

## 9. ลำดับการสร้าง

เปิดทีละขั้น ใช้กลุ่มนำร่องก่อนเปิดให้ 400 คน

**14 ก.ย. 2569 ผู้ใช้ให้เริ่มจากงานการเงินที่ทำหน้าที่จ่ายเงินก่อน** (ขั้น 4 เดิม) เริ่มจาก
ตามเอกสารจ่ายเงินชุดจริงเข้าไปใน SSB ดู `docs/finance_payment.md`

| ขั้น | ส่วนที่สร้าง | ผู้ใช้นำร่อง |
|---|---|---|
| 1 | ตัวชี้วัดกลุ่ม ก (ยา) · ล็อกอิน · บทบาท · ค้นหา · หน้ารายการ | ผู้บริหาร + คลังยา |
| 2 | ขยายตัวชี้วัดกลุ่ม ก ครบ 4 กลุ่ม | + คลังพัสดุ |
| 3 | ใบ PO ทุกคลัง + คิวงานจัดซื้อและการติดตาม | + งานจัดซื้อ งานรับของ |
| 4 | การเงิน (หลังเอกสารยืนยันที่มา) | + การเงิน |
| 5 | เครื่องช่วยหายใจและงานซ่อม | + ช่าง |
| ก่อนเปิดทุกขั้น | ทดสอบโหลด · สำรองข้อมูล · คู่มือสั้น | |

## 10. ความเสี่ยงที่ต้องยอมรับ

- **คนดูแลน้อย ผู้ใช้มาก** บั๊กตัวเดียวกระทบ 400 คน จึงต้องเปิดทีละกลุ่ม มีเทสต์ครอบ
  และมีช่องทางแจ้งปัญหาที่ชัดเจน
- **ความคาดหวังเรื่องข้อมูลสด** ข้อมูลช้ากว่า SSB ตามรอบดึง ต้องบอกผู้ใช้ตั้งแต่แรก
- **Stock5 กับ ERPLPH ทำงานซ้อนกัน** (MOS, ใบ PO, ค้นเอกสาร) ระยะยาวควรเหลือแหล่ง
  ข้อมูลเดียว ยังไม่ทำตอนนี้
